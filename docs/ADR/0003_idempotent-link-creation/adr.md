# ADR-0003: 멱등한 링크 생성

- 상태: 채택
- 결정일: 2026-07-29

## 배경

BATON과 ROUND가 링크를 원격 생성할 때 서버는 저장을 완료했지만 응답이 유실될 수 있다.
기존 무작위 발급을 그대로 재시도하면 여러 링크가 생기고, DB에 원문 코드를 저장하지
않으므로 최초 단축 URL을 복구할 수도 없다.

## 결정

- `POST /api/v1/links`는 링크 생성 요청마다 소문자 정규 UUID `Idempotency-Key`를 요구한다.
  UUID 버전은 `1..5`, 변형은 RFC 변형만 허용하며 대문자나 nil UUID를 정규화하지
  않는다.
- 과거 배포에서 이미 성공한 링크 생성 요청에는 재시도 시 기존 결과를 반환한다. 당시 UUID 파서가 허용한
  정규 대문자, nil, 버전 `0`·`6..f`, 비 RFC 변형은 소문자로 정규화해 기존 예약만 조회한다.
  해당 키 해시의 기존 예약이 있을 때만 요청 내용과 코드 해시를 검증해 결과를 반환하고,
  예약이 없으면 `400 INVALID_IDEMPOTENCY_KEY`로 거부한다. 이 경로는
  새 예약이나 링크를 저장하지 않는다.
- 관리 JWT 발급 키와 별개인 `BATON_GO_LINK_CODE_SECRET`을 사용한다.
- 공개 코드는
  `first16(HMAC-SHA-256(secret, "baton-go-link-code:v1\0" + idempotencyKey))`로 파생한다.
- DB에는 공개 코드와 멱등성 키의 SHA-256 해시만 저장한다.
- `link_creation_requests`가 멱등성 키 해시와 링크 ID를 연결한다.
- `link_creation_requests`는 최초 생성에 사용한 정규 공개 출처도 함께 저장한다.
  재시도 시 저장 출처와 다시 파생한 공개 코드를 결합해 최초 단축 URL을 복원한다.
  저장 출처를 확인할 수 없으면 현재 설정으로 추정하지 않고 요청을 거부한다.
  세부 결정은 ADR-0009를 따른다.
- 일반 `INSERT`와 MySQL 고유 키 잠금으로 같은 요청의 중복 저장을 막는다. Spring이 변환한
  `DuplicateKeyException`만 재시도로 처리하고, 다른 저장 오류는 숨기지 않는다. 중복 삽입이
  끝나면 먼저 예약을 저장한 트랜잭션이 커밋된 상태이므로 일반 조회로 완성된 링크를 읽는다.
- 같은 키와 요청 내용으로 재시도하면 기존 URL을 반환하고, 같은 키의 다른 요청 내용은 `409`로 거부한다.
- 생성 요청의 `notBefore`와 `expiresAt`은 마이크로초 단위로 정확히 표현되고 Java/JDBC가
  역산 그레고리력 `Instant`를 MySQL `DATETIME(6)` 원시 값과 동일하게 보존하는
  `1582-10-15T00:00:00Z` 이상
  `9999-12-31T23:59:59.999999Z` 이하인 값만 받는다. 더 세밀하거나 범위 밖인 값을 DB
  정밀도·범위에 맞춰 절삭하거나 보정하면 서로 다른 요청을 같은 내용으로 판정할 수
  있으므로 링크 생성 예약·저장 전에 `400 INVALID_REQUEST`로 거부한다.
- 과거 배포가 지원 저장 범위 안의 더 세밀한 입력을 마이크로초로 절삭해 이미 저장한
  링크 생성 요청의 재시도만 허용한다. 기존 예약을 먼저 조회하고 같은 마이크로초 절삭 요청 내용이
  저장값과 일치할 때만 기존 결과를 반환한다. 예약이 없으면 새 행 없이 `400 INVALID_REQUEST`, 범위 밖이면
  예약 여부와 무관하게 `400 INVALID_REQUEST`다.
- 재시도 응답은 링크의 현재 폐기 상태를 반환한다.

## 트랜잭션 경계

예약 생성, 링크 생성과 저장은 하나의 트랜잭션에서 수행한다. 먼저 예약을 저장한 트랜잭션이
롤백되면 예약 행도 함께 사라지고, 대기 중인 다른 요청이 예약을 저장할 수 있다.

과거 UUID 또는 나노초 정밀도 호환 요청은 새 예약을 저장하지 않는다.
기존 예약을 읽은 뒤 DB 원문 조회 결과, 정규 대상, 마이크로초 요청 내용과
현재 HMAC 코드 해시가 모두 일치할 때만 기존 결과를 반환한다.

먼저 예약을 저장한 트랜잭션이 롤백되면 같은 고유 키를 기다리던 일부 트랜잭션은
MySQL 교착 상태로 실패할 수 있다. 실패한 트랜잭션 전체를 롤백한 뒤 호출자가 같은
멱등성 키와 요청 내용으로 재시도한다. 다른 요청이 링크를 저장했다면 해당 링크를 반환한다.

중복 삽입을 시도한 트랜잭션이 이어서 `SELECT ... FOR UPDATE`로 배타 잠금을 얻으려 하면
교착이 발생할 수 있으므로 후속 조회에는 비관 잠금을 사용하지 않는다.
이 동작은 MySQL Testcontainers의 동시 요청 테스트로 검증한다.

## 운영 결과

- 서비스 재시작, 복제본 변경과 DB 복구 뒤에도 같은 비밀값을 사용해야 같은 URL을 복원할 수 있다.
- 키 묶음과 키 버전을 도입하기 전에는 링크 코드 파생 비밀값을 회전하지 않는다.
- ADR-0004에 따라 시작 시점과 신규 생성 예약 전에 HMAC 파생 버전·지문을 DB의
  단일 식별 정보와 대조한다. 빈 DB만 자동 결합하며 기존 데이터가 있는 미결합 DB와
  식별 정보 불일치가 있으면 시작·생성을 거부한다.
- 재시도 시 현재 파생한 코드 해시가 저장값과 다르면 동작하지 않는 URL을 반환하지 않고
  설정 불일치로 실패한다. DB에 키 정보를 등록한 뒤에도 손상과 구현 오류를 잡기 위해 이 검사를 유지한다.
- BATON과 ROUND는 원본 데이터의 트랜잭션이 커밋된 뒤 GO를 호출한다.
  링크 생성 요청 UUID는 아웃박스 또는 원본 데이터에 보존한다.
- 관리 JWT와 링크 코드 파생 비밀값을 로그와 URL에 넣지 않는다.
