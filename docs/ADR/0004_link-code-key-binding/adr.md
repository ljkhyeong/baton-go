# ADR-0004: 링크 코드 HMAC 키와 데이터베이스 결합

> 단일 키 운영과 회전 금지는 [ADR-0011](../0011_link-code-key-ring/adr.md)로 대체했다.
> 아래 내용은 최초 결합과 단일 키 배포의 배경이며, 현재 키 교체는 ADR-0011과 운영 절차를 따른다.

- 상태: 채택
- 결정일: 2026-08-02

## 배경

공개 코드는 멱등성 키와 `BATON_GO_LINK_CODE_SECRET` 비밀값의 HMAC으로 결정된다. 다른 비밀값으로
기존 생성 요청을 재시도하면 다른 공개 코드가 만들어지므로 ADR-0003은 저장된 코드 해시와
현재 파생 결과를 비교해 잘못된 URL 반환을 막았다.

서버와 `guard-tool`에 서로 다른 비밀값 관리자 버전이 주입되면 같은 배포에서도 서로 다른
HMAC 키 식별 정보가 되어 시작·복원 계약을 만족할 수 없다.

하지만 기존 요청의 재시도 전에는 설정 오류를 발견하지 못한다. 잘못된 비밀값으로 시작한
복제본이 새 링크 생성 요청을 먼저 처리하면 한 데이터베이스에 서로 다른 키로 파생된 링크가
섞이고, 어느 비밀값으로도 모든 링크의 URL을 복원할 수 없게 된다.

## 결정

- Flyway가 `link_code_key_guard` 단일 행 `guard_id=1`을 만든다.
- 단일 행은 링크 코드 파생 규약 버전과 HMAC 키 지문을 함께 저장한다.
- 식별 정보는 다음 값으로 고정한다.
  - 버전: `hmac-sha256-link-code-v1`
  - 지문:
    `hex(HMAC-SHA-256(secret, "baton-go-link-code-key-fingerprint:v1\0"))`
- 지문은 비밀값 자체가 아니지만 로그, 오류 응답과 운영 티켓에 기록하지 않는다.
- 서버와 `guard-tool`은 같은 비밀값 관리자 버전의 `BATON_GO_LINK_CODE_SECRET`을 사용한다.
  새 비밀값은 표준 설정 파서와 충돌하지 않는 base64url/16진수 알파벳으로 생성한다.
- 애플리케이션 시작의 `ApplicationRunner`가 현재 식별 정보와 DB 식별 정보를 검증한다.
- 링크 생성 트랜잭션은 예약 행을 만들기 전에 같은 검증을 다시 수행한다.
- DB 식별 정보가 이미 결합되어 있으면 버전과 지문이 모두 일치해야 한다.
- 미결합 상태에서는 `smart_links`와 `link_creation_requests`가 모두 비어 있을 때만 현재
  식별 정보에 자동 결합한다.
- 불일치, 부분 결합, 단일 행 유실 또는 기존 데이터가 있는 미결합 상태는 같은
  오류로 실패하며 비밀값과 지문을 메시지에 포함하지 않는다.
- ADR-0003의 URL 복원 시 코드 해시 검증은 손상과 구현 실수를 막는 방어 계층으로 유지한다.

## 동시성과 트랜잭션 경계

시작 검증은 단일 행을 `SELECT ... FOR UPDATE`로 잠그고 식별 정보와 업무 테이블의 빈
상태를 확인해 필요하면 결합한다. 같은 식별 정보를 가진 복제본은 최초 결합 뒤 모두 통과한다.
서로 다른 식별 정보의 복제본이 빈 DB에서 동시에 시작하면 먼저 잠근 하나만 결합하고 나머지는
불일치로 실패한다.

생성 경로는 자동 결합하지 않고 `SELECT ... FOR SHARE` 현재 읽기로 이미 결합된 식별 정보만
검증한다. 공유 잠금은 정상 생성끼리 호환되므로 단일 행 때문에 전역 직렬화되지 않고,
MySQL `REPEATABLE READ`의 과거 스냅샷을 만들지 않아 다른 요청이 커밋한 예약을 읽을 수 있다.
시작 실행기보다 요청이 먼저 도착해 단일 행이 미결합이면 저장 전에 실패한다.

시작 검증과 웹 서버 초기화 사이에 생성 요청이 들어올 수 있으므로 시작 검증만 신뢰하지
않는다. `SmartLinkService.createLink`가 같은 보호 장치를 생성 예약보다 먼저 확인해, 검증 실패
시 링크와 예약이 한 건도 저장되지 않게 한다.

## 배포와 복구

신규 DB는 Flyway가 미결합 단일 행을 만든 뒤 시작 검증이 자동 결합한다.

기존 링크나 생성 예약이 있는 DB는 현재 비밀값을 증명할 원문 멱등성 키가 없으므로 자동
결합하지 않는다. 최초 도입은 다음 순서를 따른다.

1. 모든 구버전 쓰기 프로세스와 생성 트래픽을 중지한다.
2. 비밀값 관리자에서 기존 배포에 사용한 불변 비밀값 버전을 복구한다.
3. 안전하게 보관한 검증용 생성 요청이 있다면 현재 파생 코드 해시와 DB의 예약-링크
   코드 해시가 같은지 오프라인으로 검증한다.
4. 검증된 배포 도구가 단일 행의 버전과 지문을 한 트랜잭션에서 결합한다.
5. 새 버전을 시작하고 준비 상태가 열리기 전에 보호 장치 검증이 통과하는지 확인한다.

검증된 배포 도구는 배포 소스에서 별도 생성하는
`guard-tool` 모듈의 `baton-go-guard-binding.jar`다. 이 모듈은 애플리케이션, 링크 코드
외부 어댑터와 MySQL JDBC를 조합하며 일반 서버의 웹 서버·Hibernate/Spring Data JPA·
Actuator 런타임을 포함하지 않는다. 일반 애플리케이션의 우회 설정값이나 관리 HTTP 엔드포인트가
아니며, 쓰기 프로세스 중지 확인 인자와 표준 입력의 검증용 생성 요청을 요구한다. 도구는 검증용
멱등성 키의 예약 해시와 현재 비밀값에서 파생한 코드 해시가 같은 저장 링크에 결합됐는지 확인한 뒤
보호 장치 행을 잠그고 같은 트랜잭션에서 최초 결합한다. 세부 절차는
[기존 DB의 HMAC 키 정보 최초 등록 절차](../../RUNBOOK/link-code-key-guard-binding.md)를
따른다.

결합 도구의 검증용 입력만 보호 장치 도입 전 생성 규칙과 호환되어야 한다. 애플리케이션의 공용
멱등 키 파서가 `UUID.fromString`으로 해석한 뒤
`parsed.toString().equalsIgnoreCase(input)`가 참인 문자열만 소문자 UUID로 정규화한다.
따라서 과거에 허용된 대문자, 버전 7, nil, non-RFC variant 검증용 요청도
검증할 수 있다. 기존 요청 재시도에 적용하는 UUID 호환 규칙을 사용하며 공개 생성 API의 소문자
버전 `1..5` RFC variant 신규 생성 계약을 완화하지 않는다.

한 번의 결합은 입력한 검증용 요청이 현재 비밀값과 일치한다는 사실만 증명한다. 과거 데이터
전체가 하나의 키로 만들어졌다는 증거나 이미 키가 섞인 DB의 교정 수단은 아니다. 혼합 키
가능성이 있으면 결합을 중단하고 별도 목록 조사와 복구 결정을 수행한다. 커밋 응답이
유실되어 결과가 불명확하면 쓰기 프로세스를 계속 중지한 채 같은 비밀값과 같은 검증용 요청으로
도구를 재실행한다. 같은 식별 정보에 이미 커밋됐다면 검증용 요청을 다시 확인하고 멱등 성공한다.

DB 일반 로그, 감사 플러그인과 쿼리 추적은 JDBC 준비된 문장의 지문과 해시
바인딩 값을 기록할 수 있다. 결합 전에 해당 로그의 매개변수 수집을 비활성화하거나
마스킹하고, 이미 수집된 DB 로그는 민감 운영 자료로 제한한다.

검증용 요청이나 검증된 비밀값 버전이 없다면 임의 비밀값에 DB를 결합하지 않는다. 링크 데이터가
필요 없다면 새 DB로 시작하고, 필요하다면 올바른 비밀값을 복구할 때까지 배포를 중단한다.
우회 환경 변수나 자동 강제 결합 옵션은 제공하지 않는다.

DB 백업과 해당 시점의 HMAC 비밀값 버전은 하나의 복구 단위다. 복구 훈련은 둘을 함께
복원하고 시작 검증과 검증용 요청의 기존 URL 반환을 확인해야 한다. 구버전과 신버전의 혼합 배포 중 비밀값을
변경하지 않는다.

## 비밀값 유출 대응

`BATON_GO_LINK_CODE_SECRET` 유출이 확인되거나 의심되면 일반 Secret 회전으로 처리하지
않는다. 실행 중인 Pod는 Secret 변경을 즉시 읽지 않고, 새 비밀값은 기존 DB 보호 정보와
일치하지 않아 새 프로세스가 시작하지 못한다. 또한 단축 링크 접속 처리는 저장된 코드 해시를 조회하므로
비밀값만 바꾸어도 기존 링크가 무효화되지 않는다.

사고 대응은 다음 순서를 지킨다.

1. 공개 `/l` 경계와 비공개 `/api/v1` 관리 경계를 모두 차단하고 BATON 호출자의
   아웃박스 전송을 중지한다. 처리 중인 요청이 없음을 확인한 뒤 애플리케이션 복제본을
   `0`으로 축소한다.
2. 현재 DB의 일관된 백업, 배포 이미지 다이제스트, Flyway 버전, 비밀값 관리자의
   버전 식별자와 접근 감사 증거를 제한된 사고 저장소에 보존한다. 비밀값, 지문,
   멱등성 키, 코드 해시와 전체 단축 URL은 증거에 복사하지 않는다.
3. 소유 서비스가 기존 링크를 폐기·재발급하고 새 파생 비밀값으로 전환할지,
   생성 요청별 키 버전과 복수 키 설정을 두는 버전별 키 묶음을 도입할지 결정한다.
   재시도 시 기존 URL 반환 보장 기간과 유출된 구 키의 사용 범위·폐기 시점까지 함께 정하며,
   버전별 키 묶음은 별도 ADR과 마이그레이션을 먼저 거친다.
4. 결정한 복구를 격리 환경에서 시험하고 보호 정보, 신규 생성·동일 요청 재시도, 기존 링크
   처리와 호출 서비스의 재시도 완료를 확인한 뒤에만 배포한다. 안전 담당자와 서비스 소유자의
   승인 전에는 쓰기·공개 경계를 다시 열지 않는다.

`guard-tool`은 올바른 기존 비밀값을 증명해 미결합 DB를 최초 결합하는 도구일 뿐이므로,
유출된 키를 새 키로 회전하거나 혼합 키 DB를 교정하는 용도로 사용하지 않는다.

## 결과

- 잘못된 비밀값이나 파생 규약으로 신규 링크가 섞이기 전에 시작·생성을 거부한다.
- 비밀값 회전은 허용하지 않는다. 회전이 필요하면 생성 요청별 키 버전, 복수 키 설정과
  단계적 배포를 포함한 버전별 키 묶음을 별도 ADR로 설계한다.
- 단축 링크 접속 처리는 원문 코드의 SHA-256 조회이므로 HMAC 보호 장치를 사용하지 않지만, 키
  불일치 프로세스는 시작 단계에서 종료된다.
