# ADR-0009: 멱등 생성의 공개 출처 보존

- 상태: 채택
- 결정일: 2026-08-09

## 배경

링크 생성 재시도는 동일한 `id`, `shortUrl`과 `Location`을 반환해야 한다. 공개 코드는
HMAC 파생과 DB 해시 검증으로 복구할 수 있지만, 기존 구현은 응답 시점의
`BATON_GO_PUBLIC_BASE_URL`로 `shortUrl`을 다시 조립했다. 재시작·복구·순차 배포에서
호스트나 포트 설정이 바뀌면 같은 링크 생성 요청이 다른 URL을 반환할 수 있었다.

공개 출처를 데이터베이스 전체 단일 값으로 고정하면 오류는 막을 수 있지만 정상적인
출처 이전도 전체 데이터 수명주기에 결합된다. 링크마다 전체 단축 URL이나 원문 공개
코드를 저장하는 방식은 기존 최소 저장 원칙과 맞지 않는다.

## 결정

- `link_creation_requests`에 생성 승자가 사용한 정규 `public_origin`을 저장한다.
- 출처는 스킴과 호스트를 소문자로 정규화하고 HTTP 80·HTTPS 443 기본 포트와 루트
  슬래시를 제거한다. 동등한 IPv6 리터럴도 같은 JDK 주소 표현으로 정규화한다.
- 비로컬 출처는 HTTPS만 허용하고 저장값은 ASCII 255자 이하여야 한다.
- 예약 경쟁의 승자가 출처를 함께 저장한다. 패자와 이후 재시도는 현재 설정이 아니라
  예약에 저장된 출처를 읽어 같은 공개 코드와 결합한다.
- 저장 출처가 없거나 비정규·비허용 값이면 현재 설정으로 보정하거나 추정하지 않고
  `PUBLIC_LINK_ORIGIN_REPLAY_UNAVAILABLE`로 안전 차단한다.
- DB에는 계속 공개 코드 원문과 전체 단축 URL을 저장하지 않는다.
- 공개 출처는 호출자 요청 내용이 아니므로 같은 멱등성 키의 요청 내용 충돌 비교 항목에는
  넣지 않는다. 서로 다른 설정의 복제본이 경쟁해도 먼저 저장한 출처가 응답 식별 정보다.

## 마이그레이션과 운영

Flyway V5는 기존 행과의 스키마 호환을 위해 `public_origin`을 null 허용으로 추가한다. 새
애플리케이션이 만든 예약은 항상 값을 저장한다. V5 이전 예약은 최초 URL을 증명할 별도
자료가 없으면 자동으로 채우지 않으며 재생 시 안전한 운영 오류로 실패한다. 검증된 최초
URL 목록이 있는 경우에만 유지보수 절차로 정규 출처를 채운다.

V5는 열 추가 관점에서는 확장 마이그레이션이지만 구 애플리케이션 기록자와의 동작 호환
마이그레이션은 아니다. V5 적용 뒤에도 구 기록자는 열을 생략한 예약을 성공시킬 수 있고 그
링크 생성 요청을 새 애플리케이션에서 재시도하면 기존 URL을 반환할 수 없다. 이미 실행 중인 배포에 V5를 도입할
때는 관리 생성 기록자를 차단·비우고 구 Pod를 0으로 만든 뒤 마이그레이션과 새 애플리케이션을
적용한다. 일반 순차 배포로 취급하지 않는다.

비공개 Kubernetes 첫 배포는 신규 GO 전용 DB를 사용하므로 모든 생성 예약이 V5 이후
형식으로 시작한다.

## 결과

- 공개 출처나 서버 설정이 달라져도 같은 링크 생성 요청에 기존 URL을 반환한다.
- 정상적인 새 출처 이전은 신규 링크 생성 요청부터 적용할 수 있어 DB 전체 식별 정보를 영구 고정하지
  않는다.
- 이전 스키마의 예약은 가용성보다 잘못된 URL 반환 방지를 우선한다.
