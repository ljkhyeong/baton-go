# 관리 작업 이력 조회와 보존

## 기록 범위

BATON GO는 다음 관리 쓰기 요청이 완료되면
`com.personal.batongo.adapter.in.web.ManagementOperationLogger`에서 `INFO` 로그를 남긴다.

| `operation` | 의미 |
| --- | --- |
| `LINK_CREATE` | 새 링크 생성 완료 |
| `LINK_CREATE_REPLAY` | 동일 생성 요청에 기존 결과 반환 완료 |
| `LINK_REVOKE` | 일반 링크 최초 폐기 완료 |
| `LINK_REVOKE_REPLAY` | 이미 폐기된 일반 링크의 반복 요청 완료 |
| `TARGET_CONTRACT_REVOKE` | 대상 규칙 위반 링크의 폐기 완료 |
| `TARGET_CONTRACT_REVOKE_REPLAY` | 이미 폐기된 대상 규칙 위반 링크의 반복 요청 완료 |

현재 트랜잭션 서비스 호출이 성공하여 컨트롤러로 반환된 뒤 기록한다. 서비스 처리나 커밋에서
예외가 발생하면 완료 로그를 남기지 않는다. 응답 전송 전 기록하므로 로그가 있어도 호출자가
HTTP 응답을 받았다는 뜻은 아니다.

관리 조회·대상 계약 점검, 공개 링크의 `GET·HEAD`, 인증·권한·입력 오류와 실패한 쓰기는 이 완료
이력에 포함하지 않는다. 직접 SQL, 별도 CLI와 애플리케이션 사용 사례의 직접 호출도 범위 밖이다.
전체 접근 감사나 DB 변경 내역을 제공하는 기능은 아니다.

## 필드와 서비스 식별

로그 메시지는 `관리 작업 완료 ` 뒤에 다음 네 필드의 한 줄 JSON을 붙인다.

```text
관리 작업 완료 {"operation":"LINK_CREATE","serviceId":"baton-service","linkId":"83a430c4-5c5d-4eb4-a815-7a5ba1fd4aae","requestId":"link-create-history"}
```

- `operation`: 위 표의 작업 종류
- `serviceId`: Spring Security가 검증한 JWT의 `sub`. 기본 `Principal.getName()`을 사용하며
  토큰을 다시 파싱하지 않는다.
- `linkId`: 완료한 작업의 내부 링크 UUID
- `requestId`: 해당 요청의 `X-Request-Id`와 같은 값

기록 시각은 기존 로그의 타임스탬프를 사용한다. 서비스 식별자의 따옴표·줄바꿈은 Jackson이
JSON 문자열로 이스케이프하며, API JSON 들여쓰기 설정과 관계없이 메시지는 한 줄로 기록한다.
JWT 원문, 다른 claim, `Authorization`, `Idempotency-Key`, 원문 공개 코드, 대상 경로,
전체 단축 URL과 비밀값은 포함하지 않는다.

발급자는 `sub`에 이름·이메일·자격 증명 대신 서비스별로 구분되는 안정된 식별자를 넣는다.
개별 최종 사용자나 작업자의 신원으로 해석하지 않는다. BATON GO의 기존 JWT 인증 조건은
변경하지 않는다. `sub`가 없으면 `serviceId`는 `null`, 빈 값이면 그대로 기록하며 다른 claim이나
요청 헤더에서 신원을 추정하지 않는다. 이런 기록은 서비스 신원 확인 자료로 사용할 수 없으므로
발급자 설정과 해당 호출자를 점검한다.

## 수집과 조회

1. 기존 중앙 로그 수집 경로가 위 로거의 `INFO` 메시지를 수집하는지 확인한다. 애플리케이션
   로거를 `WARN` 이상으로 올리거나 수집기에서 해당 메시지를 제외하면 이력은 남지 않는다.
2. 중앙 로그에서 로거 이름과 `관리 작업 완료 ` 메시지로 좁힌 뒤, 뒤쪽 JSON을 파싱해
   `serviceId`, `linkId`, `requestId`, `operation`으로 조회한다. 전체 JWT나 단축 URL을 검색키로
   입력하지 않는다.
3. `requestId`와 호출 서비스의 처리 기록을 함께 확인한다. 이 값은 호출자가 재사용할 수
   있으므로 고유 이벤트 ID로 취급하지 않는다.
4. 재시도는 별도의 완료 로그를 만든다. `LINK_CREATE_REPLAY`, `LINK_REVOKE_REPLAY`,
   `TARGET_CONTRACT_REVOKE_REPLAY`를 신규 생성이나 최초 폐기 건수에 합산하지 않는다.

## 보존과 보장 범위

- 기존 중앙 로그의 보존 기간, 접근 권한과 삭제 정책을 적용한다. BATON GO에 별도 감사 DB,
  로컬 이력 파일, 조회 API나 자동 삭제 작업을 추가하지 않는다.
- 운영자는 적용 중인 중앙 로그 정책의 이름·보존 기간·담당자·조회 권한을 배포 검증 기록에 남긴다.
  저장소에서 기간을 임의로 정하거나 중앙 로그 설정을 변경하지 않는다.
- DB 커밋과 로그 수집은 하나의 트랜잭션이 아니다. 커밋 직후 프로세스 종료, 로그 출력·전송 실패,
  수집 누락이나 보존 만료로 이력이 없을 수 있다. 따라서 로그가 없다는 이유만으로 작업이
  실행되지 않았다고 판단하지 않는다.
- 무손실·변조 방지 감사 원장과 정확히 한 번 기록은 보장하지 않는다. 이런 보장이 필요하면
  보존·접근 정책과 함께 트랜잭션 기반 감사 저장을 별도 설계해야 한다.

## 운영 연결 확인

비공개 관리 API에서 시험용 서비스 JWT와 시험용 링크로 생성·동일 요청 재시도·일반 링크의 최초·반복
폐기·대상 규칙 위반 링크 폐기를 실행한다.
중앙 로그에서 서비스 식별자·내부 링크 ID·요청 ID와 작업 종류가 맞는지, 인증 실패와 거부된
쓰기에는 완료 로그가 없는지, 민감 필드가 들어오지 않는지 확인한다. 정리 기능은 기존
[대상 계약 점검·폐기 절차](target-contract-v1-remediation.md)의 활성화 조건을 먼저 따른다.
로컬 테스트 통과는 중앙 수집·조회 권한·보존 정책의 운영 검증을 대신하지 않는다.
